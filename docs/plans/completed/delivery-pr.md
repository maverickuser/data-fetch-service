# PR 07: processor delivery and acceptance

Base: `stack/06-pull` (`d94ba82`). Branch: `stack/07-delivery`.

The Delivery Lambda consumes a run reference from SQS, claims the queued handoff, and loads the exact immutable manifest selected by PR 06. Its processor request is a separate structured CloudEvent containing `data.manifest.bucket/key` and matching dataset metadata, never `data.files`. The submission bytes, ID, time, and `Idempotency-Key` are stable across HTTP attempts. The Lambda stores the submission before its first send and creates a separate started/finished record for each attempt.

The pinned processor configuration permits at most three HTTP attempts. Go's automatic transport replay is disabled so one started record represents at most one POST. A valid HTTP 202 receipt is written before the run is completed; the existing recoverable coordinator transition then writes durable acceptance evidence and advances the deduplication baseline. A disabled processor, terminal HTTP status, or exhausted budget fails the run without baseline advancement; exhausted wholly unknown outcomes use `DELIVERY_OUTCOME_UNKNOWN`. Network loss and 429/500/503 responses retry the same request. The immutable finished record retains `finished_at` and `retry_after_seconds`; a delay exceeding the invocation budget leaves recovery work rather than sending early.

`RecoverAccepted` completes a run from durable 202 evidence without another processor call, repairing the coordinator's reserved transition when needed. It can recover a missing accepted record from a finished attempt. A lost finished write remains an unknown attempt and must consume the next HTTP attempt when PR 08 resumes delivery. SQS redelivery cannot silently acknowledge an unfinished run as stale.

The unit suite covers BSE/NSDL submission profiles, stable retries, terminal and retryable responses, malformed receipts, attempt records, S3 reader bounds, partial SQS failures, and a lost completion write after accepted receipt evidence. Real coordinator fault injection covers accepted-record creation, completion reservation, acceptance evidence, history, and finalization. An in-memory transport regression checks that a lost HTTP response cannot trigger a hidden POST replay. The separate mocked HTTP integration test exercises the service with a real `http.Client` and an in-memory processor handler. No live processor or AWS resource is used in this increment.
